5 Manager Flow /pm

The /pm command has four modes, detected automatically from input.

/pm [description]     → BASE — new project or version
/pm catch-up        → CATCH-UP — retroactive baseline
/pm [tier 1 link]    → BREAKDOWN — tier 1 → tier 2
/pm triage          → TRIAGE — intake → versioned work

5a. BASE Protocol — New Project / Version

1
Discovery
Discuss idea with user. Ask relevant questions. Present feature set grouped by modules, ordered by implementation dependency.
2
Context Gathering
Collect: Plane Project ID, Outline Root Doc ID, module deadlines, lead user per module, version decision (new or update), check for unfinished work.
3
Confirm
Present complete plan to user. Do not proceed without explicit confirmation.
4
Execute
a) Update docs/index.md with Plane + Outline IDs
b) Create Plane modules (name, dates, lead, status: planned)
c) Create Outline docs: spec docs under Specifications/, version parent + module docs under Versions/
d) Cross-link Plane ↔ Outline bidirectionally
e) Create tier 1 seed work items (Backlog state, no estimate)

5b. BREAKDOWN Protocol — Tier 1 → Tier 2

1
Verify
Confirm work item is tier 1 (no parent). Confirm NOT Done (sealed versions block new tier 2). Read attached Outline version doc.
2
Decompose
Break into feature-level behaviors (WHAT, not HOW). Each tier 2 gets pass/fail criteria. Assign Fibonacci estimates (max 8 — split 13s).
3
Confirm & Create
Present breakdown with estimates. On approval: create tier 2 items (Todo state), update tier 1 to Todo, assign engineers.
⚠
Tier 2 = behavior, not implementation. Write "Google OAuth login with dashboard redirect" — NOT "Build auth hook, create login component." The HOW is the engineer's job.

5c. CATCH-UP Protocol — Existing Project Baseline

For projects with working code but no PM structure. Creates a retroactive baseline so future work follows the normal flow.

Same artifacts as BASE, but all statuses are completed/Done:

  • • Plane modules → status: completed
  • • Outline specs → written from existing code
  • • Tier 1 seeds → state: Done
  • • No tier 2/3/4 created — baseline only

6a. /p — Plan Implementation

/p [tier 2 link] — new plan   |   /p [temp file] — resume existing plan
1
Read Context
Fetch tier 2 from Plane (title, requirements, spec link). Read module spec from Outline (both sections). Read related module specs if linked.
2
Assess & Discuss
Evaluate feasibility. Q&A rounds with user until approach is clear: component architecture, schema changes, edge cases, phase ordering.
3
Create Plan File
Break tier 2 into phases (A, B, C...) and tasks. Write plan file at cycles/[YYYY-WW]/[module]/[tier1]/[tier2]-[slug].md. User must confirm.
4
Update Status
Tier 2 → In Progress. Tier 1 parent → In Progress (if not already).

Rich Temp File Structure

# [Tier 2 Title] Work Item: [SPARK-N] (plane_link) Module: [Module Name] (module_link) Outline Spec: [spec_link] Version Doc: [version_link] ## Context (from spec) Non-tech: [stakeholder description] Tech: [files, components, tables] Related: [Module] (link) - [why] ## Phase A: [Name] - [ ] Task 1 description - [ ] Task 2 description ## Phase B: [Name] - [ ] Task 1 description --- ## Plane IDs (populated by /pp) Phase A: (pending) - Task 1: (pending)

6b. /s — Execute Task

/s [task description]
/s [temp file] [phase] [task]
1
Build Skills Map
Scan all .claude/skills/*/SKILL.md headers. Identify which skills are relevant to this task.
2
Research Codebase
Explore existing code if needed. Note hidden systems and dependencies.
3
Re-evaluate Skills (Mandatory)
After research, revisit the skills map. Research often reveals hidden needs (auth patterns, hooks, DB changes).
4
Load & Validate
Load all relevant skills (once each). Check for conflicts with loaded skill patterns. Stop if conflicts found.
5
Execute & Update
Implement the task. Mark completed tasks [x] in the temp file. Report applied skills.
ⓘ
No MCP calls during /s — all work is local only. Context comes from the temp file, not from Plane or Outline. This saves token budget and keeps execution fast.

6c. /pp — Push + Condense

/pp [temp file path]
1
Deep Research (Hard Gate)
Read every file in temp file's Tech context. Verify implementation matches phases/tasks. Cannot skip this step.
2
Create Work Items on Plane
Create tier 3 (phases) and tier 4 (tasks) — all as Done. Clone properties from tier 2. Add to module + cycle.
3
Mark Tier 2 Done
Update tier 2 state to Done. Update its cycle to current week.
4
Auto-Condense Spec
Rewrite (not append) the Outline spec doc: Non-Technical + Technical sections reflect the current state. Append one-line version link to Version History.
5
Create/Update Version Doc
At Versions/[vX.Y.Z]/[Module]: add summary, implementation details, SPARK-N work item links, changed files.
6
Auto-Complete Tier 1
If ALL sibling tier 2 items are Done → mark tier 1 as Done and module as completed. Version is now sealed.

Triage Decision Tree

For each intake item:

1. Which module(s) does this touch?
2. Is there an active (not Done) tier 1 for this module?

YES — Active Tier 1 Exists
Add tier 2 under existing tier 1. No version bump needed.
NO — Version Sealed / No Tier 1
Determine version bump:
• Patch — bug fix / small tweak
• Minor — new feature, non-breaking
• Major — breaking change / redesign
Create new tier 1 + tier 2.
✔
Batch related intake items. Review ALL pending intake before triaging. Group related requests for the same module into one version bump to keep version history clean.

Version Sealing Rule

🔒
A completed version is sealed permanently. Once a tier 1 reaches Done, no new tier 2 items can be added under it. Any new work on that module requires a version bump and a new tier 1.
Tier 1 StateCan Add Tier 2?Action
Backlog / Todo / In Progress Yes Add via /pm breakdown or triage
Done No — Sealed Must bump version → new tier 1

9 Outline Document Structure

Outline is the single source of truth for all specifications. No local spec files are maintained.

Spark (Root Doc) ├── Specifications/ ← Current state of all modules │ ├── Module A/ │ │ └── Sub-module/ │ └── Module B/ ├── Versions/ ← Semver snapshots │ ├── v1.0.0/ │ │ ├── Module A/ │ │ └── Module B/ │ └── v1.1.0/ │ └── Module A/ (only changed modules) └── Cycles/ ← Weekly cycle reports ├── YYYY/WW/ └── YYYY/WW/

Module Spec Doc (under Specifications/)

Section 1: Non-Technical

Stakeholder-readable. 2-4 sentences + capability bullets. Current state only — rewritten on each /pp, never appended.

Section 2: Technical

Engineer-readable. File paths, component tree, DB schema, API endpoints, data flow, related modules. Current state only.

Section 3: Version History

Minimal one-line links. Format: - [vX.Y.Z](link) — summary. Appended by /pp.

Version Doc (under Versions/vX.Y.Z/)

Snapshot of what changed in a module for a specific version:

  • • Navigation links (back to spec doc + Plane module)
  • • Summary (3-5 bullets of implementation)
  • • Requirements (from tier 2 items)
  • • Implementation details (phases + tasks with SPARK-N links)
  • • New/changed files list

10 Story Point Estimation

Fibonacci scale, only on tier 2 items. Set by the manager. Reflects total human effort (planning + review + debugging).

PointsComplexityWhat It Touches
1 Single concern One file, one table, or one component. No new patterns.
2 Two connected concerns Backend + frontend change, or a new route with simple page.
3 One end-to-end slice New table + RLS + edge function + component. One vertical.
5 Multiple coordinated slices New schema + RLS + edge functions + route + multiple components + state.
8 Cross-cutting / high-uncertainty Auth + middleware + multiple routes + policies. New patterns. High debug risk.
13 TOO LARGE Must decompose before estimating. Multiple 5-pt tasks hiding inside.

Estimation Rules

  1. Count distinct concerns: DB, RLS, edge functions, routes, components, state, integrations
  2. Assess debug risk: auth, RLS, race conditions, realtime → +1-2 points
  3. Assess novelty: new pattern for the codebase → +1 point
  4. If estimate = 13 → must split into smaller items
  5. Maximum allowed estimate on a single tier 2: 8

Report Structure

Executive Summary

3-5 sentences. What was delivered, total points, top modules. Past tense.

Points Summary

Total points with version breakdown. Module-by-module table with feature count and points.

What Was Delivered

Per-module sections with non-technical descriptions and feature lists. Present tense.

Technical Changes

Per-module technical implementation from spec docs. Routes, components, schema.

Grouping Rules

Module TypeTreatment
Major (3+ tier 2 features) Full section: description + feature list + technical details
Minor (1-2 tier 2, non-trivial) Condensed section, still individual
Namespace/rename Grouped together under one heading
Baseline (catch-up, 0 tier 2) Single grouped paragraph
⚠
Done only. Reports never include in-progress, backlog, or todo items. Only completed work with Done state is reported. Points are always shown alongside feature counts.
